# Design LeetCode

## 1. Functional Requirements

### User Management

Allow users to:

- Register and log in.
- Manage their profiles.
- Track solved problems.
- Track contest participation.
- Track ratings and progress.
- View submission history.

### Problem Database

Provide a categorized repository of coding problems including:

- Problem statements
- Difficulty levels
- Topics and tags
- Company-specific filters
- Constraints
- Examples
- Test cases
- Editorials and explanations

### Code Execution

Provide a real-time code editor that supports:

- Multiple programming languages
- Code compilation
- Test case execution
- Output validation
- Runtime measurement
- Memory measurement
- Submission status

Possible submission results:

```text
AC  → Accepted
WA  → Wrong Answer
TLE → Time Limit Exceeded
MLE → Memory Limit Exceeded
RE  → Runtime Error
CE  → Compilation Error
```

### Contests

Host:

- Live contests
- Virtual contests
- Contest problems
- Real-time leaderboards
- Contest rankings
- Submission tracking

### Discussion Forums

Provide community features for:

- Problem discussions
- Solution explanations
- Code sharing
- Comments
- Upvotes
- Community interaction

### Learning Modules

Offer:

- Tutorials
- Problem sets
- Curated learning paths
- Algorithms
- Data structures
- Interview preparation

### Analytics

Track:

- Problems solved
- Submission success rate
- Contest rating
- Ranking
- Difficulty distribution
- Topic-wise performance
- Skill improvement over time

---

# 2. Non-Functional Requirements

- **Scalability:** Handle millions of users and concurrent code submissions globally.
- **Low Latency:** Provide near-instant feedback on code execution and submissions.
- **High Availability:** Ensure uptime during peak usage and contests.
- **Security:** Protect user code and submissions from unauthorized access or malicious execution.
- **Data Integrity:** Ensure accuracy of problem data, user progress and rankings.
- **Cross-Platform Support:** Provide a seamless experience across web, mobile and desktop platforms.
- **User Experience:** Provide a responsive and fast coding experience.
- **Isolation:** Ensure untrusted user code cannot affect the underlying infrastructure.

---

# 3. Consistency / Availability

## Consistency > Availability

LeetCode requires stronger consistency for critical data such as:

- User submissions
- Submission results
- Contest rankings
- Problem metadata
- Contest state
- User ratings
- Contest finalization

Eventual consistency can be used for less critical data such as:

- Analytics
- Notifications
- Discussion counters
- Recommendation data
- Non-critical activity statistics

During contests, correctness of submissions and rankings is more important than serving stale ranking data.

## User APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/register` | Register a new user |
| `POST` | `/login` | Authenticate users |
| `GET/PUT` | `/profile` | Fetch and update user details |

## Problem APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/getProblems` | Fetch problems based on difficulty, tags, etc. |
| `GET` | `/getProblemDetails` | Retrieve details of a specific problem |

## Submission APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/submitCode` | Submit code for execution and validation |
| `GET` | `/getSubmissionResult` | Fetch the result of a code submission |

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/getContestDetails` | Fetch ongoing/upcoming contest details |
| `POST` | `/submitContestSolution` | Submit a solution for a contest problem |

# Code Execution Architecture

User-submitted code is **untrusted code** and must never execute directly on application servers.

```text
                    USER CODE
                       │
                       ▼
               ┌───────────────┐
               │ Submission Svc│
               └───────┬───────┘
                       │
                       ▼
               ┌───────────────┐
               │ Message Queue │
               │    Kafka      │
               └───────┬───────┘
                       │
                       ▼
               ┌───────────────┐
               │ Execution Mgr │
               └───────┬───────┘
                       │
             ┌─────────┼─────────┐
             │         │         │
             ▼         ▼         ▼
         Worker 1   Worker 2   Worker N
         Sandbox    Sandbox    Sandbox
             │         │         │
             └─────────┼─────────┘
                       │
                       ▼
                Test Results
                       │
                       ▼
               Submission Service
                       │
                       ▼
                    User
```

- CPU limits
- Memory limits

- Process limits

## Relational Database

Use **MySQL / PostgreSQL** for strongly consistent transactional data:

- User profiles
- Problem metadata
- Contest metadata
- Contest results
- Ratings
- User progress
- Submission metadata

Example:

```text

Problems
Contests
ContestParticipants
Submissions

```

## NoSQL Database

Use **MongoDB / DynamoDB** for flexible, high-volume data:

- Code submissions
- Discussion forums
- Activity events
- Execution logs
- User activity data

## Redis

Use Redis for:

- Problem lists
- User progress
- Session data
- Contest state
- Leaderboards
- Frequently accessed problem metadata
- Rate limiting

## Blob Storage

Use **Amazon S3 / GCS / Azure Blob Storage** for:

- Problem images
- Tutorial videos
- Learning materials
- Large execution artifacts
- Other media files

# 10. Failure & Fault Tolerance

## Replication

Replicate:

- User data
- Problem data
- Submission metadata
- Contest data
- Ratings
- User progress

across multiple database nodes.

## Sandbox Isolation

User code must execute in isolated environments.

```text
              Application Servers
                       │
                       ▼
                Execution Queue
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    Sandbox 1      Sandbox 2      Sandbox N
        │              │              │
        ▼              ▼              ▼
     User Code      User Code      User Code
```

A compromised or infinite-loop submission must not affect other users or infrastructure.

## Fallback Mechanism

If execution workers are temporarily unavailable:

```text
Submission
    │
    ▼
Kafka Queue
    │
    X
Workers Unavailable
    │
    ▼
Submission Remains Queued
    │
    ▼
Workers Recover
    │
    ▼
Submission Processed
```

This prevents submission loss during temporary execution-service outages.

## Circuit Breakers

Prevent cascading failures.

```text
Submission Service
        │
        ▼
Execution Service
        │
        X
     Failure
        │
        ▼
  Circuit OPEN
        │
        ▼
Queue Submission
```

## Additional Fault-Tolerance Techniques

- Health checks
- Automatic worker replacement
- Dead-letter queues
- Retry with exponential backoff
- Idempotent event processing
- Request timeouts
- Rate limiting
- Backpressure
- Graceful degradation

# Security

### Authentication

1. Use OAuth 2.0 / secure authentication mechanisms.
2. Use HTTPS/TLS.
3. Use short-lived access tokens.
4. Protect refresh tokens.
5. Apply role-based access control.

### Code Execution Security

1. Run every submission inside an isolated sandbox.
2. Apply CPU limits.
3. Apply memory limits.
4. Apply execution timeouts.
5. Disable unnecessary network access.
6. Restrict filesystem access.
7. Restrict process creation.
8. Use container isolation.
9. Monitor abnormal execution behavior.
10. Destroy the sandbox after execution.

### Submission Security

1. Encrypt submissions at rest.
2. Encrypt submissions in transit.
3. Prevent unauthorized access to private submissions.
4. Apply access control to execution results.
5. Audit submission access.

### Plagiarism Detection

Use plagiarism detection systems to:

- Detect copied solutions
- Compare code structure
- Identify suspicious submissions
- Maintain contest integrity

Possible systems include:

```text
Submission A
     │
     ▼
Code Normalization
     │
     ▼
Similarity Engine
     │
     ▼
Submission B / C / D
     │
     ▼
Similarity Score
     │
     ▼
Review / Detection
```

# Key Design Principles

- **Microservices-based architecture**
- **Sandboxed code execution**
- **Kafka-based asynchronous submission processing**
- **Horizontal execution-worker scaling**
- **Redis for caching and leaderboards**
- **Relational databases for strongly consistent data**
- **NoSQL for high-volume flexible data**
- **Object storage for large media**
- **WebSockets for real-time contest updates**
- **Contest-based sharding**
- **Read replicas for read-heavy workloads**
- **Strong consistency for submissions and rankings**
- **Eventual consistency for non-critical analytics**
- **Multi-region deployment**
- **Automatic worker replacement**
- **Circuit breakers and retries**
- **Rate limiting**
- **Plagiarism detection**
- **Centralized logging and monitoring**
- **Strict sandbox isolation**
- **Secure execution of untrusted code**

# Most Important Design Decision

The **code execution pipeline is the most critical and security-sensitive component**.

User code must never run directly inside the API or application servers.

```text
                         CODE EXECUTION HOT PATH

User
 │
 ▼
API Gateway
```
