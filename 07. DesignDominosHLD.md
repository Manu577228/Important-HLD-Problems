# Design Domino's

## 1. Functional Requirements

### User Registration and Authentication

Users should be able to:

- Sign up using their phone number or email address.
- Log in to their account.
- Manage their profile.
- Manage saved delivery addresses.
- View their order history.

### Menu Management

Display a dynamic menu containing:

- Pizzas
- Toppings
- Crust options
- Sizes
- Drinks
- Desserts
- Combos
- Promotional items

Users should be able to customize pizzas with different toppings and available options.

### Order Placement

Users should be able to:

1. Select items from the menu.
2. Customize their items.
3. Add items to the cart.
4. Specify delivery details.
5. Apply promotions.
6. Select a payment method.
7. Place the order.
8. Track the order.

### Payment Integration

Support secure payment options such as:

- Credit cards
- Debit cards
- Digital wallets
- Online banking
- Other supported payment methods

Payment processing should be handled through a secure third-party payment gateway.

### Order Tracking

Provide real-time order tracking through different stages:

```text
Order Placed
     ↓
Payment Confirmed
     ↓
Order Accepted
     ↓
Preparing
     ↓
Ready for Pickup
     ↓
Out for Delivery
     ↓
Delivered
```

### Delivery Management

Assign delivery drivers based on:

- Proximity
- Availability
- Delivery region
- Current workload

The system should provide real-time delivery updates.

### Promo Codes and Discounts

Users should be able to:

- Apply promo codes.
- Receive discounts.
- Use promotional offers.
- Validate eligibility.
- See the final discounted price.

### Ratings and Reviews

Users should be able to rate and review:

- Pizza
- Food quality
- Delivery service
- Overall ordering experience

---

# 2. Non-Functional Requirements

- **Scalability:** Handle traffic spikes during weekends, holidays, sports events and promotional campaigns.
- **Low Latency:** Users should experience minimal delays while browsing menus, placing orders and tracking deliveries.
- **High Availability:** Maintain 99.99% uptime, particularly for ordering and payment systems.
- **Security:** Protect user information, payment details and order history.
- **Data Integrity:** Ensure consistency for order status, payments and inventory.
- **Global Availability:** Support multiple regions with localized menus, pricing, taxes and currencies.
- **Reliability:** Ensure successful order processing even during traffic spikes.
- **Performance:** Maintain responsive application performance across web and mobile clients.

---

# 3. Consistency / Availability

## Consistency > Availability

Strong consistency should be used for critical operations such as:

- Payment transactions
- Order creation
- Order totals
- Inventory updates
- Promo-code validation
- Refunds
- Payment status

Eventual consistency can be used for:

- Order tracking
- Driver location
- Notifications
- Analytics
- Reviews
- Non-critical activity updates

The most important rule is:

```text
Payment + Order Creation
        ↓
Strong Consistency
        ↓
No Duplicate Charge
        ↓
No Duplicate Order
```

# Payment Flow

```text
User
 │
 │ Checkout
 ▼
Order Service
 │
 │ Calculate Final Amount
 ▼
Payment Service
 │
 ▼
Payment Gateway
 │
 ├── Success
 │      │
 │      ▼
 │  Payment Confirmed
 │      │
 │      ▼
 │  Order Confirmed
 │
 └── Failure
        │
        ▼
    Payment Failed
```

Payment must be **idempotent**.

Example:

```text
Same Payment Request
        │
        ▼
Idempotency Key
        │
        ▼
Payment Service
        │
        ├── First Request  → Charge
        │
        └── Duplicate      → Return Existing Result
```

This prevents duplicate charges during retries.

# 10. Failure & Fault Tolerance

## Data Replication

Replicate important data across multiple nodes and regions.

Critical data includes:

- Orders
- Payments
- Users
- Menu
- Inventory
- Driver assignments

## Retry Mechanisms

Use:

- Exponential backoff
- Request timeouts
- Maximum retry limits
- Idempotency keys

```text
Request
   │
   ▼
Payment Service
   │
   X Temporary Failure
   │
   ▼
Retry
   │
   ▼
Payment Gateway
   │
   ▼
Success
```

Payment retries must never result in duplicate charges.

## Graceful Degradation

During failures or extreme load:

```text
High Traffic
    │
    ▼
System Load
    │
    ├── Menu ──────────────► ACTIVE
    │
    ├── Order Placement ──► ACTIVE
    │
    ├── Payment ───────────► ACTIVE
    │
    ├── Tracking ──────────► ACTIVE
    │
    ├── Reviews ───────────► DEGRADED
    │
    └── Recommendations ──► DEFERRED
```

Core ordering and payment functionality should remain operational.

## Fallback Strategies

Possible fallback mechanisms:

- Read replicas
- Cached menus
- Cached store information
- Redundant payment providers
- Retry queues
- Dead-letter queues
- Backup notification providers

## Circuit Breakers

Prevent cascading failures.

```text
Order Service
      │
      ▼
Payment Service
      │
      X
   Failure
      │
      ▼
Circuit OPEN
      │
      ▼
Order Remains Payment Pending
```

# Security

### Data Protection

1. Encrypt sensitive data at rest.
2. Encrypt data in transit using HTTPS/TLS.
3. Never store raw card details when a secure payment tokenization mechanism is available.
4. Protect user addresses and personal information.
5. Secure payment records.

### Authentication

1. Use OAuth 2.0.
2. Use JWT or secure session tokens.
3. Implement secure password handling.
4. Support OTP-based authentication.
5. Apply token expiration and rotation.

### Authorization

Use role-based access control.

```text
Customer
   │
   ├── Browse Menu
   ├── Place Order
   ├── Track Order
   └── Review Order

Restaurant Staff
   │
   ├── View Orders
   ├── Update Order Status
   └── Manage Menu

Delivery Driver
   │
   ├── View Assigned Orders
   ├── Update Location
   └── Update Delivery Status

Admin
   │
   ├── Manage Users
   ├── Manage Stores
   ├── Manage Menu
   ├── Manage Promotions
   └── View Analytics
```

### Additional Security

- Regular vulnerability assessments
- Penetration testing
- Rate limiting
- DDoS protection
- Input validation
- Audit logging
- Fraud detection
- Secure payment tokens
- Access control
- Secret management

# Key Design Principles

- **Microservices-based architecture**
- **Event-driven order processing**
- **Kafka / RabbitMQ for asynchronous events**
- **Redis for menu, sessions and delivery state**
- **Relational database for orders and payments**
- **NoSQL for high-volume tracking data**
- **Blob storage for images and promotional media**
- **WebSockets for real-time order tracking**
- **Geo-based driver assignment**
- **Regional database partitioning**
- **Horizontal scaling**
- **Read replicas**
- **Idempotent payment processing**
- **Strong consistency for financial transactions**
- **Eventual consistency for tracking and notifications**
- **Multi-region replication**
- **Graceful degradation**
- **Circuit breakers and retries**
- **Secure payment processing**
- **Centralized logging and monitoring**
- **Fraud detection and rate limiting**

# Most Important Design Decision

The **order + payment path is the critical business path**, while **delivery tracking is the critical real-time path**.

Both should be designed independently:

```text
                    DOMINO'S CRITICAL PATHS


             ORDER + PAYMENT PATH
                     │
                     ▼
                  User
                     │
                     ▼
              Order Service
                     │
                     ▼
             Payment Service
                     │
                     ▼
             Payment Gateway
                     │
                     ▼
             Order Confirmed
                     │
                     ▼
                Restaurant
                     │
                     ▼
              Delivery Service


             REAL-TIME TRACKING PATH
                     │
                     ▼
                 Driver
                     │
                     │ GPS
                     ▼
              Location Service
                     │
                     ▼
                Redis Geo
                     │
                     ▼
             WebSocket / PubSub
                     │
                     ▼
               Customer App
```

The **payment flow must be strongly consistent and idempotent**, while the **tracking pipeline should prioritize low latency and availability**.
