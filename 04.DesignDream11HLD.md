# Design Dream11

## 1. Functional Requirements

### User Authentication and Profile

Users must register and log in to create and manage their fantasy team profiles.

Users can maintain:

- Personal profile
- Authentication details
- Fantasy teams
- Contest participation
- Wallet and transaction history

### Create and Join Contests

Users should be able to:

- Create custom contests
- Join pre-existing contests
- View contest details
- View entry fees
- View prize pools
- View contest rules
- Track contest status

### Team Formation

Users can create fantasy teams by selecting players under a predefined virtual budget.

The team creation system should validate:

- Total budget
- Number of players
- Player categories
- Team composition
- Captain selection
- Vice-captain selection
- Contest-specific rules

### Live Match Updates

Provide real-time updates for:

- Match score
- Player performance
- Runs
- Wickets
- Catches
- Assists
- Goals
- Other sport-specific events

The scoring engine converts these events into fantasy points.

### Leaderboard and Rankings

Display rankings based on fantasy team performance.

Leaderboards should support:

- Real-time ranking updates
- Player fantasy points
- Team score
- Rank changes
- Contest standings
- Final rankings

### Prize Distribution

After a contest ends:

1. Determine final rankings.
2. Calculate winners.
3. Calculate prize amounts.
4. Process payouts.
5. Update wallet balances.
6. Store transaction history.

---

## 2. Non-Functional Requirements

- **Scalability:** Handle millions of concurrent users, especially during popular matches.
- **Low Latency:** Provide real-time updates with minimal delay.
- **High Availability:** Ensure the platform remains operational during critical match timings.
- **Security:** Safeguard user data and transactions using encryption and secure payment gateways.
- **Data Accuracy:** Ensure real-time data integrity for match updates and fantasy-point calculations.
- **Compliance:** Adhere to legal and regulatory requirements for skill-based gaming in different regions.
- **Reliability:** Ensure scoring, rankings, contests and payments remain reliable during traffic spikes.
- **User Experience:** Provide a responsive interface with real-time updates.

---

## 3. Consistency / Availability

### Availability > Consistency

The platform should prioritize availability during high-traffic sporting events.

Eventual consistency can be used for:

- Live scores
- Player statistics
- Fantasy points
- Leaderboards
- Notifications
- Non-critical analytics

Strong consistency should be used for critical operations such as:

- Contest entry
- Wallet transactions
- Prize distribution
- Payment transactions
- Team locking
- Contest finalization

The system must ensure that a user cannot:

- Join a closed contest
- Edit a locked team
- Receive duplicate payouts
- Spend the same wallet balance twice


This decouples high-volume match events from user-facing services.

# 7. Kind of Data Store

## Relational Database

Use **MySQL / PostgreSQL** for transactional data:

- User profiles
- Contest details
- Team metadata
- Contest participation
- Wallet transactions
- Payment transactions
- Prize distribution
- Audit records

## NoSQL Database

Use **MongoDB / DynamoDB** for high-volume operational data:

- Live match statistics
- Player events
- Fantasy scoring data
- Match events
- High-throughput data

## Redis

Use Redis for:

- Live scores
- Leaderboards
- User sessions
- Active contests
- Frequently accessed match data
- Rate limiting

## Blob Storage

Use **Amazon S3 / GCS / Azure Blob Storage** for:

- Player images
- Contest banners
- Team images
- Static media
- Other large files

# 8. Scaling of DB

## Horizontal Scaling

Partition data using:

```text
contestId
userId
matchId
```

Example:

```text
                    Global Traffic
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
         Contest A    Contest B    Contest C
             │            │            │
             ▼            ▼            ▼
          Shards        Shards        Shards
```

## Replication

Use read replicas to handle high query traffic.

```text
                 Primary DB
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Read 1     Read 2     Read 3
```

Read replicas can handle:

- Leaderboard reads
- Contest browsing
- Player statistics
- Match information

Write operations remain directed to the primary database where strong consistency is required.



For leaderboard-heavy workloads, partitioning by `contestId` is useful because most leaderboard queries are scoped to a specific contest.

# 10. Failure & Fault Tolerance

## Replication

Ensure data is replicated across multiple nodes to avoid single points of failure.

Critical data includes:

- User data
- Teams
- Contest participation
- Wallet transactions
- Payment records
- Final rankings

## Fallback Mechanisms

During temporary database outages:

```text
Request
   │
   ▼
Redis Cache
   │
   ├── HIT ───────► Serve Cached Data
   │
   └── MISS
          │
          ▼
       Database
          │
          X
       Failure
          │
          ▼
     Replica / Retry
```

Cached live scores and rankings can continue to serve users during temporary backend failures.

## Circuit Breakers

Prevent cascading failures between services.

```text
Leaderboard Service
        │
        ▼
Scoring Service
        │
        X
     Failure
        │
        ▼
  Circuit OPEN
        │
        ▼
Fallback / Cached Score
```

## Additional Fault-Tolerance Techniques

- Health checks
- Automatic failover
- Multi-region replication
- Dead-letter queues
- Idempotent event processing
- Request timeouts
- Retry with exponential backoff
- Rate limiting
- Graceful degradation
- Backpressure

## Security

1. Encrypt sensitive user data at rest.
2. Encrypt data in transit using HTTPS/TLS.
3. Secure APIs using OAuth 2.0 and HTTPS.
4. Use secure payment gateways.
5. Protect wallet and transaction APIs.
6. Apply role-based access control.
7. Implement rate limiting.
8. Protect APIs against DDoS attacks.
9. Use fraud detection systems.
10. Detect duplicate or suspicious contest activity.
11. Monitor abnormal user behavior.
12. Maintain immutable transaction/audit logs.
13. Perform regular vulnerability assessments.
14. Perform penetration testing.
15. Follow applicable gaming, KYC and payment regulations.

# Key Design Principles

- **Microservices-based architecture**
- **Event-driven match processing**
- **Kafka for high-throughput match events**
- **Redis for live scores and leaderboards**
- **Redis Sorted Sets for ranking**
- **Relational databases for transactional data**
- **NoSQL databases for high-volume match events**
- **WebSockets for real-time updates**
- **Horizontal database scaling**
- **Contest-based sharding**
- **Read replicas for leaderboard reads**
- **External sports-data integration**
- **Secure payment gateway integration**
- **Fraud and abuse detection**
- **Idempotent prize distribution**
- **Multi-region replication**
- **Circuit breakers and retries**
- **Centralized logging and monitoring**
- **High availability during peak match traffic**
- **Strong consistency for money and contest finalization**
- **Eventual consistency for non-critical live updates**

# Most Important Design Decision

The **live scoring and leaderboard path is the critical hot path** during a major match.

Therefore:

```text
                       LIVE SCORING HOT PATH

External Sports Provider
          │
          │ Live Match Event
          ▼
   Event Ingestion Service
          │
          ▼
        Kafka
          │
          ▼
    Scoring Service
          │
          ├──────────────► Player Points
          │
          ▼
      Team Scores
          │
          ▼
   Leaderboard Service
          │
          ▼
    Redis Sorted Set
          │
          ▼
      WebSocket
          │
          ▼
       User Apps
```

The scoring pipeline should be **asynchronous, horizontally scalable and idempotent**, while Redis provides low-latency access to live scores and rankings.
