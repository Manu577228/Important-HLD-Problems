# Design Uber Backend

## 1. Functional Requirements

### User Registration and Authentication

Users and drivers must register with their credentials such as:

- Phone number
- Email
- Password / OTP
- Profile information

Users and drivers must be authenticated securely during login.

### Real-Time Ride Booking

Users can request a ride by providing:

- Pick-up location
- Drop-off location
- Vehicle type
- Ride preferences

### Driver Matching

Match riders with the nearest available driver based on:

- Driver location
- Driver availability
- Vehicle type
- Distance
- Estimated arrival time

### Live Tracking

Enable riders to track their driver's real-time location throughout the ride.

### Pricing and Payment

Dynamically calculate fares based on:

- Distance
- Time
- Vehicle type
- Demand
- Surge pricing

Process payments securely after ride completion.

### Ratings and Feedback

Allow both riders and drivers to:

- Rate each other
- Provide feedback
- Report issues

### Trip History

Maintain completed-trip history for:

- Riders
- Drivers
- Payments
- Ratings
- Ride status

---

## 2. Non-Functional Requirements

- **Scalability:** Support millions of ride requests and GPS updates globally.
- **Low Latency:** Ensure minimal delay in driver matching and location updates.
- **High Availability:** Maintain 99.99% uptime with global coverage and redundancy.
- **Security:** Encrypt sensitive data and secure all communication channels.
- **Data Durability:** Prevent data loss through replication and backups.
- **Reliability:** Guarantee successful ride-request processing under heavy load.
- **User Experience:** Provide a seamless, responsive interface with real-time updates.

---

## 3. Consistency / Availability

### Availability > Consistency

Prioritize high availability while maintaining eventual consistency for:

- Ride status updates
- Driver location
- Driver availability
- Notifications
- Non-critical analytics

Strong consistency should be used where correctness is critical, especially for:

- Payments
- Ride completion
- Financial transactions

# 4. APIs

## User APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/register` | Register a user or driver |
| `POST` | `/login` | Authenticate user or driver |

## Ride APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/bookRide` | Submit a ride request |
| `GET` | `/getRideStatus` | Retrieve ongoing ride status |
| `POST` | `/completeRide` | Mark a ride as completed |

## Payment APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/calculateFare` | Calculate estimated fare |
| `POST` | `/processPayment` | Process ride payment |

## Driver APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/updateLocation` | Update driver's GPS coordinates |
| `POST` | `/setAvailability` | Update driver's availability |

# 5. Architecture

## Microservices Architecture

Separate services handle different responsibilities:

```text
                    ┌─────────────────────┐
                    │     API Gateway     │
                    └──────────┬──────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
        ▼                      ▼                      ▼
 ┌──────────────┐       ┌──────────────┐       ┌──────────────┐
 │ User Service │       │ Ride Service │       │Location Svc  │
 └──────────────┘       └──────────────┘       └──────────────┘
        │                      │                      │
        ▼                      ▼                      ▼
 ┌──────────────┐       ┌──────────────┐       ┌──────────────┐
 │Payment Svc   │       │Notification  │       │Rating Service│
 └──────────────┘       │Service       │       └──────────────┘
                        └──────────────┘
```

### Load Balancer

Distribute incoming requests among multiple application servers.

Responsibilities include:

- Traffic distribution
- Health checks
- Failover
- SSL termination
- Global routing

### Event-Driven Communication

Use **Kafka / RabbitMQ** for asynchronous events:

- Ride requested
- Driver matched
- Ride accepted
- Ride started
- Location updated
- Ride completed
- Payment completed
- Notification events

# 7. Kind of Data Store

## Relational Database

Use **MySQL / PostgreSQL** for strongly consistent transactional data:

- User profiles
- Driver profiles
- Ride history
- Payment transactions
- Ratings
- Financial records

## NoSQL Database

Use **MongoDB / Cassandra** for high-volume operational data:

- Real-time ride information
- Driver availability
- Ride events
- Location updates
- High-throughput workloads

## Spatial Database

Use **PostGIS** for geospatial queries:

- Nearby-driver search
- Geofencing
- Location indexing
- Distance calculations
- City/region queries

## Cache

Use **Redis** for:

- Nearby drivers
- Driver availability
- Sessions
- Active rides
- Frequently accessed ride information

# 8. Scaling of DB

## Horizontal Scaling

Partition data geographically:

```text
                    Global Traffic
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
         US Region    Europe Region   Asia Region
             │            │            │
             ▼            ▼            ▼
          Shards        Shards        Shards
```

This reduces cross-region traffic and improves latency.

## Replication

Use replicas for:

- High availability
- Disaster recovery
- Read scalability
- Failover

Example:

```text
             Primary DB
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      Read 1   Read 2   Read 3
```

# 9. Caching & Sharding

## Caching

Use **Redis / Memcached** for frequently accessed data:

- User sessions
- Nearby drivers
- Active rides
- Driver availability
- Pricing information
- Frequently accessed metadata

Example:

```text

   ▼

   ├── Cache Hit ──────► Response
   │

            ▼
```

```text

      ▼
```

```text

```

For location-heavy workloads, geographic partitioning is especially useful.

# 10. Failure & Fault Tolerance

## Replication

Replicate critical data across multiple nodes and regions.

## Fallback Mechanism

Use retries with exponential backoff for transient failures.

```text
Request
   │
   ▼
Service A
   │
   X Failure
   │
   ▼
Retry
   │
   ▼
Service B
   │
   ▼
Success
```

## Circuit Breakers

Prevent cascading failures:

```text
Ride Service
     │
     ▼
Payment Service
     │
     X
  Failure
     │
     ▼
Circuit OPEN
     │
     ▼
Fallback / Fast Failure
```

## Additional Techniques

- Health checks
- Automatic failover
- Multi-region replication
- Dead-letter queues
- Idempotent APIs
- Request timeouts
- Rate limiting
- Graceful degradation
- Backpressure

# 11. Logging & Security

## Logging

Use centralized logging with the **ELK Stack**:

```text
Microservices
     │
     ▼
Log Collectors
     │
     ▼
Elasticsearch
     │
     ▼
Kibana
```

Monitor:

- Request latency
- Driver matching latency
- GPS update rates
- Ride failures
- Payment failures
- API errors
- Database performance
- Service health

## Security

1. Encrypt sensitive data at rest.
2. Encrypt data in transit using HTTPS/TLS.
3. Use OAuth 2.0 / secure authentication mechanisms.
4. Protect payment information.
5. Apply role-based access control.
6. Use rate limiting.
7. Protect APIs against DDoS attacks.
8. Perform regular vulnerability assessments.
9. Perform penetration testing.
10. Audit sensitive operations.

# Key Design Principles

- **Microservices-based architecture**
- **Event-driven communication**
- **Kafka for asynchronous ride events**
- **Redis for real-time location and driver availability**
- **Geospatial indexing for driver matching**
- **PostGIS for location-based queries**
- **WebSockets for real-time tracking**
- **Relational databases for transactional data**
- **NoSQL databases for high-volume operational data**
- **Geographic partitioning for global scale**
- **Multi-region replication**
- **Dynamic pricing and surge management**
- **Fault isolation using circuit breakers**
- **Retries with exponential backoff**
- **99.99% availability target**
- **End-to-end secure communication**
- **Centralized logging and monitoring**
