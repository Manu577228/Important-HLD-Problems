# Design Docker

---

# 1. Functional Requirements

## Containerization

Docker should allow users to package:

- Application code.
- Runtime dependencies.
- Libraries.
- Configuration.
- Environment-specific requirements.

Everything required to run an application should be packaged into a portable container image.

```text id="1rj6w2"
Application Code
      +
Dependencies
      +
Runtime
      +
Configuration
      │
      ▼
Docker Image
      │
      ▼
Container
```

The same container image should be runnable across development, testing and production environments.

---

# Image Creation

Users should be able to create Docker images using a `Dockerfile`.

A Dockerfile can specify:

- Base image.
- Application dependencies.
- Environment variables.
- Files to copy.
- Commands to execute.
- Exposed ports.
- Startup command.

Example:

```dockerfile
FROM ubuntu:22.04

WORKDIR /app

COPY requirements.txt .

RUN apt-get update && \
    apt-get install -y python3 python3-pip

RUN pip3 install -r requirements.txt

COPY . .

EXPOSE 8080

CMD ["python3", "app.py"]
```

The Docker Engine processes the Dockerfile and creates a layered image.

---

# Image Registry

Docker images should be stored and distributed through registries.

Examples:

- Docker Hub.
- Private registries.
- Cloud registries.
- Enterprise registries.

# Networking

Docker should provide networking capabilities so containers can communicate with:

- Other containers.
- Host systems.
- External services.
- The internet.

Supported networking concepts include:

- Bridge networks.
- Overlay networks.
- Network drivers.
- Container-to-container communication.
- DNS/service discovery.

---

# Volume Management

Containers are designed to be replaceable, so persistent application data should be stored outside the writable container layer.

Docker volumes allow:

- Persistent data.
- Shared files.
- Database storage.
- Container-independent data.

```text id="k8kn5s"
     │

```

Docker-based workloads can be managed using orchestration tools such as:

- Docker Compose.
- Kubernetes.
- Docker Swarm.

Orchestration can provide:

- Multiple container deployment.
- Service management.
- Scaling.
- Load balancing.
- Health checks.
- Failover.

# 2. Non-Functional Requirements

## Scalability

Docker should support running large numbers of lightweight containers.

```text id="1c6x7m"
                 Application
                      │
                      ▼
              Container Image
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      Container A  Container B  Container C
          │           │           │
          └───────────┼───────────┘
                      ▼
                 More Replicas
```

Containers can be horizontally scaled across multiple machines.

---

## Performance

Docker should provide:

- Lightweight execution.
- Efficient CPU utilization.
- Efficient memory usage.
- Fast startup.
- Image-layer reuse.
- Build caching.

---

## High Availability

Containerized applications should support:

- Multiple replicas.
- Automatic restart.
- Health checks.
- Load balancing.
- Failure recovery.
- Distributed deployment.

If one container fails, another healthy instance can continue serving traffic.

---

## Security

Docker should provide isolation between containers.

Security mechanisms include:

- Linux namespaces.
- Control groups.
- Seccomp.
- AppArmor/SELinux.
- User permissions.
- Network isolation.
- Image scanning.

---

## Portability

The same image should be usable across:

```text id="z2r7nb"
Development
     │
     ▼
Testing
     │
     ▼
Staging
     │
     ▼
Production
```

This reduces environment-specific inconsistencies.

# Image Layer Architecture


# 8. Caching & Sharding

# Docker Build Cache

Docker caches image build layers.

```text id="m7q2kp"

    │
    ▼

    │
    ▼
Cached Layer
    │
    ▼
Instruction 2
    │
    ▼
Cached Layer
    │
    ▼
Changed Instruction
    │
    ▼
Rebuild From Changed Layer
```

This avoids rebuilding unchanged layers.

---

# Image Layer Reuse

Suppose:

```text id="y4p9ds"
Image A
 ├── Ubuntu
 ├── Python
 ├── Dependencies
 └── App A

Image B
 ├── Ubuntu
 ├── Python

 └── App B
```

```text id="6g2k8w"

     │
```

- Build time.

# Most Important Design Decisions

## 1. Images Are Immutable Application Artifacts

The core Docker workflow is:

```text id="r8k2w5"
Source Code
    │
    ▼
Dockerfile
    │
    ▼
Immutable Image
    │
    ├── Development
    ├── Testing
    ├── Staging
    └── Production
```

The same image can be promoted through environments instead of rebuilding the application differently for each environment.

---

# 2. Containers Should Be Disposable

A container should generally be treated as replaceable.

```text id="m7c4x9"
Container A
    │
    X
  Failure
    │
    ▼
Orchestrator
    │
    ▼
Container B
    │
    ▼
Same Image
    │
    ▼
Application Continues
```

Persistent state should be stored in volumes or external data systems rather than relying on the container's writable layer.

---

# 3. Images and Containers Are Different

```text id="2s7v5n"
Docker Image
     │
     │ docker run
     ▼
Container
```

**Image** = immutable package/template.

**Container** = running instance of an image.

One image can create many containers:

```text id="8q4m1x"
                  Docker Image
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     Container A  Container B  Container C
```

---

# 4. Build Cache Is Critical for Developer Productivity

Docker's layered image architecture allows unchanged layers to be reused.

```text id="6k9p3r"
Dockerfile
    │
    ▼
Layer 1 ─── Cached
    │
    ▼
Layer 2 ─── Cached
    │
    ▼
Layer 3 ─── Cached
    │
    ▼
Layer 4 ─── Changed
    │
    ▼
Rebuild From Layer 4
```

This dramatically reduces repeated build work.

---

# 5. Containers Need Orchestration at Scale

Running a few containers can be handled directly with Docker commands.

At large scale:

```text id="f3q7m8"
Hundreds / Thousands of Containers
              │
              ▼
         Orchestrator
              │
      ┌───────┼────────┐
      ▼       ▼        ▼
   Scaling  Health   Scheduling
            Checks
      │       │        │
      └───────┼────────┘
              ▼
        Desired State
```

The orchestrator maintains the required application state across machines.
