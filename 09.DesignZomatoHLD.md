# Design Zomato

---

# 1. Functional Requirements

## User Registration and Authentication

Users should be able to:

- Register using phone number or email.
- Log in securely.
- Update their profile.
- Manage delivery addresses.
- View their previous orders.
- Maintain secure authentication sessions.

Authentication can support OTP-based login, password-based login and MFA.

---

## Restaurant Search

Users should be able to discover restaurants based on:

- Current location.
- Delivery address.
- Cuisine.
- Restaurant name.
- Ratings.
- Price range.
- Distance.
- Availability.
- Delivery time.

The system should rank restaurants based on relevance, distance, rating, availability and other business rules.

---

## Restaurant Menu

Each restaurant should have a dynamic menu containing:

- Dishes.
- Categories.
- Prices.
- Discounts.
- Images.
- Availability.
- Nutritional information.
- Customization options.
- Add-ons.

Restaurant menus should be independently manageable by restaurants.

---

## Order Placement

Users should be able to:

1. Select a restaurant.
2. Browse the menu.
3. Select multiple dishes.
4. Customize dishes.
5. Add items to the cart.
6. Apply promotional offers.
7. Select delivery or pickup.
8. Select an address.
9. Make payment.
10. Place the order.
11. Track the order.

---

## Payment Integration

Support secure payment methods such as:

- Credit cards.
- Debit cards.
- Digital wallets.
- UPI.
- Other supported online payment methods.
- Cash on Delivery where applicable.

Payment processing should be handled through secure third-party payment providers.

---

## Reviews and Ratings

Users should be able to:

- Rate restaurants.
- Review restaurants.
- Rate individual dishes.
- Submit delivery feedback.
- View restaurant reviews.
- View dish reviews.

Reviews should preferably be associated with completed orders.

---

## Order Tracking

Users should be able to track an order through:

```text
ORDER PLACED
      ↓
RESTAURANT ACCEPTED
      ↓
PREPARING
      ↓
READY FOR PICKUP
      ↓
OUT FOR DELIVERY
      ↓
DELIVERED
```

Tracking should provide near-real-time status updates.

---

## Delivery Management

The system should assign delivery partners based on:

- Proximity.
- Availability.
- Current workload.
- Delivery route.
- Restaurant location.
- Customer location.

The system should support real-time driver location updates.

---

## Discounts and Promotions

Users should be able to:

- Apply promo codes.
- Receive restaurant-specific discounts.
- Receive platform offers.
- Receive loyalty-based offers.
- Receive cart-level discounts.
- Receive eligible payment offers.

The promotion service should validate eligibility before applying discounts.

---

# 2. Non-Functional Requirements

## Scalability

The system should support:

- Millions of users.
- Large restaurant catalogs.
- Large menu datasets.
- High concurrent searches.
- Peak meal-time traffic.
- Large numbers of concurrent orders.
- High-volume delivery tracking.

Microservices should scale horizontally based on traffic.

---

## Low Latency

Critical operations should have low response times:

- Restaurant search.
- Restaurant details.
- Menu loading.
- Cart updates.
- Checkout.
- Order status.
- Delivery tracking.

Caching and geographically distributed services should be used to reduce latency.

---

## High Availability

The platform should target:

**99.99% availability**

Critical systems include:

- Restaurant discovery.
- Menu browsing.
- Cart.
- Checkout.
- Payment.
- Order placement.
- Delivery tracking.

---

## Security

Protect:

- User information.
- Phone numbers.
- Email addresses.
- Delivery addresses.
- Payment information.
- Order history.
- Authentication credentials.

Use:

- HTTPS/TLS.
- Encryption at rest.
- JWT/OAuth2.
- MFA.
- RBAC.
- Rate limiting.
- Audit logging.

---

## Data Integrity

Data consistency is particularly important for:

- Orders.
- Payments.
- Restaurant acceptance.
- Order status.
- Delivery assignment.
- Inventory/availability.
- Refunds.

---

## Global Availability

The system should support:

- Multiple countries.
- Localized menus.
- Local currencies.
- Local payment methods.
- Regional restaurant availability.
- Region-specific delivery options.

---

# 3. Consistency / Availability

## Consistency > Availability

For Zomato, consistency is more important for critical transactional operations.

Strong consistency should be used for:

- Order creation.
- Payment transactions.
- Order amount.
- Restaurant order acceptance.
- Promo validation.
- Refunds.
- Critical inventory/availability checks.

Eventual consistency can be used for:

- Driver location.
- Order tracking.
- Notifications.
- Search indexes.
- Ratings.
- Recommendations.
- Analytics.

---

## Why Strong Consistency for Payments?

Consider:

```text
User
 │
 ▼
Checkout
 │
 ▼
Payment Request
 │
 ├──────────────► Request A
 │
 └──────────────► Request B
```

Without idempotency:

```text
Request A → Payment Success
Request B → Payment Success

       ↓

Customer charged twice
```

With idempotency:

```text
Payment Request
      │
      ▼
Idempotency Key
      │
      ▼
Payment Service
      │
      ├── First Request → Process
      │
      └── Duplicate     → Return Existing Result
```

# 8. Scaling of DB

# Horizontal Scaling

Distribute data across multiple database nodes.

```text
                    Database Cluster
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Shard A       Shard B       Shard C
```

Possible shard keys:

- Region.
- Restaurant ID.
- User ID.
- Order ID.

---

# Regional Partitioning

Zomato has location-heavy traffic, so geographical partitioning can reduce latency.

```text
India
 │
 ├── North
 │
 ├── South
 │
 ├── East
 │
 └── West
```

Restaurant and order traffic can be routed toward the appropriate regional infrastructure.

---

# Order Sharding

Orders can be partitioned by:

```text
Region
   │
   ├── North
   ├── South
   ├── East
   └── West
```

or by:

```text
hash(order_id) % N
```

Regional partitioning is useful when most order operations are naturally associated with a geographic location.

---

# Replication

Use primary-replica replication.

```text
                    Primary DB
                        │
             ┌──────────┼──────────┐
             ▼          ▼          ▼
         Replica 1   Replica 2   Replica 3
```

Benefits:

- High availability.
- Read scalability.
- Disaster recovery.
- Failover.

# Most Important Design Decisions

## 1. Restaurant Discovery Must Be Location-Aware

Restaurant search is not simply a text search.

```text
User Location
      │
      ▼
Geo Search
      │
      ▼
Nearby Restaurants
      │
      ├── Cuisine
      ├── Rating
      ├── Price
      ├── Availability
      ├── Delivery Time
      └── Distance
      │
      ▼
Ranked Results
```

---

## 2. Payment Must Be Idempotent

```text
Payment Request
      │
      ▼
Idempotency Key
      │
      ▼
Payment Service
      │
      ├── New Request
      │      │
      │      ▼
      │   Process Payment
      │
      └── Duplicate Request
             │
             ▼
        Existing Result
```

This prevents duplicate charges during retries.

---

## 3. Delivery Matching Must Be Real-Time

```text
Order Ready
     │
     ▼
Available Drivers
     │
     ▼
Nearby Drivers
     │
     ▼
Distance + Load + Availability
     │
     ▼
Best Driver
     │
     ▼
Assigned
```

---

## 4. Restaurant Acceptance Is Part of the Order Lifecycle

A payment can succeed while a restaurant may reject the order because of:

- Restaurant closure.
- Dish unavailability.
- Capacity constraints.
- Operational issues.

Therefore the order system needs explicit states for acceptance, rejection and refund handling.

---

## 5. Real-Time Tracking Should Be Decoupled

The core order record should remain durable while high-frequency driver location updates are handled separately.

```text
Order DB
   │
   │ Durable Order State
   ▼
Order Service

Driver GPS
   │
   │ High Frequency
   ▼
Location Service
   │
   ▼
Redis / NoSQL
   │
   ▼
WebSocket
   │
   ▼
Customer
```

This prevents high-frequency location writes from overwhelming the transactional order database.

# Final Takeaway

The Zomato backend should use a **microservices + event-driven architecture** where restaurant discovery, ordering, payment, restaurant operations and delivery are independently scalable.

The core journey is:

```text
Restaurant Discovery
        ↓
Restaurant Menu
        ↓
Cart
        ↓
Promo
        ↓
Order
        ↓
Payment
        ↓
Restaurant Acceptance
        ↓
Food Preparation
        ↓
Driver Assignment
        ↓
Real-Time Tracking
        ↓
Delivery
        ↓
Review
```

The three most important guarantees are:

```text
       ┌────────────────────────────────┐
       │         ZOMATO CORE            │
       ├────────────────────────────────┤
       │                                │
       │  1. Never double-charge        │
       │                                │
       │  2. Never lose an order        │
       │                                │
       │  3. Deliver real-time status   │
       │                                │
       └────────────────────────────────┘
```

Everything else—reviews, recommendations, promotions, analytics and other secondary features—should be independently degradable so that the core **search → menu → cart → payment → restaurant → delivery** journey remains available during failures or extreme traffic.

## Final Architecture in One Line

**Location-aware discovery + microservices + strong transactional ordering/payment + event-driven processing + Redis caching + geospatial delivery matching + real-time tracking + horizontal scaling + fault-tolerant infrastructure.**
