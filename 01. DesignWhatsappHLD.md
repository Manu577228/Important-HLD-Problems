# Design WhatsApp

## 1. Functional Requirements

- **User Registration and Authentication:** Users must be able to register using a phone number and log in.
- **Real-Time Messaging:** Allow one-on-one and group text messaging with message delivery status (sent, delivered, read).
- **Multimedia Sharing:** Users should share images, videos, documents, and voice notes.
- **Push Notifications:** Notify users of new messages when the app is in the background.
- **Group Management:** Create, join, or leave groups with a limit on participants.
- **Encryption:** End-to-end encryption for all messages and calls.
- **Voice and Video Calls:** Peer-to-peer voice and video calling.

---

## 2. Non-Functional Requirements

- **Scalability:** Support millions of concurrent users globally.
- **Low Latency:** Messages and calls should have minimal delay.
- **High Availability:** 99.99% uptime with minimal maintenance windows.
- **Security:** Use end-to-end encryption to ensure user privacy.
- **Data Durability:** Messages must not be lost even during system failures.
- **Cross-Platform Support:** Provide seamless experience on iOS, Android, and Web.
- **User Experience:** Provide a responsive, fast, and user-friendly interface.

---

## 3. Consistency / Availability

- **Availability > Consistency:** Focus on high availability using eventual consistency for messages and notifications to ensure the system is always operational.

---

## 4. APIs

### User APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/register` | Register a user with a phone number |
| `POST` | `/login` | Authenticate and log in the user |

### Messaging APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/sendMessage` | Send a text or multimedia message |
| `GET` | `/fetchMessages` | Retrieve conversation history |

### Call APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/startCall` | Initiate a voice or video call |
| `POST` | `/endCall` | Terminate a call |

### Group APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/createGroup` | Create a new group |
| `POST` | `/addMember` | Add a user to a group |

---

## 5. Architecture

### Microservices-Based Architecture

Separate services are responsible for:

- User management
- Authentication
- Messaging
- Groups
- Notifications
- Voice and video calls
- Media processing

### Load Balancer

Distributes incoming traffic across multiple application servers to provide:

- High availability
- Horizontal scalability
- Load distribution
- Failure recovery

### Event-Driven Communication

Use a distributed message broker such as **Kafka** for:

- Real-time events
- Message delivery
- Delivery confirmations
- Read receipts
- Push notification events
- Call signaling
- User presence

## 7. Kind of Data Store

### NoSQL Database

Use **Cassandra / DynamoDB** for message storage because of:

- High write throughput
- Horizontal scalability
- Large-scale distributed storage
- Partition-based access
- High availability

### Relational Database

Use **MySQL / PostgreSQL** for:

- User profiles
- Authentication metadata
- Group metadata
- User settings
- Administrative data

### Blob Storage

Use **Amazon S3 / GCS / Azure Blob Storage** for:

- Images
- Videos
- Documents
- Voice notes
- Other large multimedia files

---

## 8. Scaling of DB

### Horizontal Scaling

Partition data using:

```text
User ID
   |
   +----> Shard 1
   |
   +----> Shard 2
   |
   +----> Shard 3
   |
   +----> Shard N
```

This allows additional database nodes to be added as traffic increases.

### Replication

Use replication to provide:

- Data durability
- High availability
- Disaster recovery
- Failover capability

For relational databases, read replicas can be used to scale read-heavy workloads.

---

## 9. Caching & Sharding

### Caching

Use **Redis / Memcached** for frequently accessed information:

- User sessions
- Recent messages
- User presence
- Group information
- Frequently accessed metadata

Example:

```text
Client
  |
  v
API Gateway
  |
  v
Redis Cache
  |
  +---- Cache Hit ----> Response
  |
  +---- Cache Miss
             |
             v
          Database
```

### Sharding

Use shard keys such as:

```text
userId
conversationId
region
```

This distributes traffic across multiple database nodes.

---

## 10. Failure & Fault Tolerance

### Replication

Replicate critical data across multiple nodes and potentially multiple regions.

### Fallback Mechanism

If a server fails:

```text
Request
   |
   v
Server A
   |
   X Failure
   |
   v
Server B
   |
   v
Success
```

### Retry Mechanism

Transient failures should trigger controlled retries with exponential backoff.

### Circuit Breakers

Circuit breakers prevent cascading failures between microservices.

```text
Service A
   |
   v
Service B
   |
   X
Repeated Failure
   |
   v
Circuit OPEN
   |
   v
Fast Failure / Fallback
```

### Additional Fault-Tolerance Techniques

- Health checks
- Automatic failover
- Multi-region replication
- Graceful degradation
- Dead-letter queues
- Idempotent APIs
- Timeouts
- Rate limiting

---

## 11. Logging & Security

### Logging

Use centralized logging such as the **ELK Stack**:

```text
Services
   |
   v
Log Collectors
   |
   v
Elasticsearch
   |
   v
Kibana
```

Monitor:

- Request latency
- Error rates
- Message delivery
- Database performance
- Service health
- Traffic patterns
- Authentication failures

### Security

- Encrypt data at rest.
- Encrypt data in transit using HTTPS/TLS.
- Use end-to-end encryption for messages and calls.
- Secure APIs using OAuth 2.0 / secure authentication mechanisms.
- Use short-lived access tokens and refresh tokens.
- Apply rate limiting.
- Protect against DDoS attacks.
- Perform regular security audits.
- Perform penetration testing.
- Use secure media URLs.
- Never expose private encryption keys to backend services.

## Key Design Principles

- **Event-driven microservices architecture**
- **WebSocket-based real-time messaging**
- **Kafka for asynchronous event processing**
- **Cassandra/DynamoDB for massive message workloads**
- **MySQL/PostgreSQL for relational metadata**
- **Redis for low-latency caching and presence**
- **Object storage for multimedia**
- **Horizontal scaling and sharding**
- **Multi-region replication**
- **End-to-end encryption**
- **99.99% availability target**
- **Fault isolation using retries, timeouts and circuit breakers**
- **Centralized logging and monitoring**
- **Cross-platform support for Android, iOS and Web**
