# Design Tiny URL

## 1. Functional Requirements

### URL Shortening

Allow users to input a long URL and generate a short URL.

### Redirection

Redirect users to the original URL when they visit the short URL.

### Custom Alias

Optionally allow users to specify custom short URLs.

### URL Analytics

Provide basic analytics such as:

- Number of clicks
- Geographic data
- Device information
- Browser information
- Timestamp
- Referrer information

### Expiration

Optionally allow users to set expiration dates for short URLs.

---

## 2. Non-Functional Requirements

- **Scalability:** Handle millions of URL shortening requests and redirections daily.
- **Low Latency:** Ensure minimal delay for redirection requests.
- **High Availability:** Maintain 99.99% uptime to prevent downtime for critical redirection services.
- **Security:** Prevent abuse such as phishing links and unauthorized access to analytics.
- **Durability:** Ensure all URLs remain valid unless explicitly expired.
- **Performance:** Short URL generation and redirection must be near-instantaneous.

---

## 3. Consistency / Availability

### Availability > Consistency

Focus on high availability with eventual consistency for:

- Analytics
- Click counts
- Geographic data
- Notifications
- Non-critical metadata

Strong consistency should be used where correctness is critical, especially for:

- Custom alias creation
- URL ownership
- URL expiration
- Primary URL mappings

---

## 4. APIs

### Shortening APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/createShortURL` | Generate a short URL for a given long URL |
| `POST` | `/customShortURL` | Create a custom short URL if available |

### Redirection APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/redirect/{shortURL}` | Redirect to the original URL |

### Analytics APIs

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/getAnalytics/{shortURL}` | Retrieve analytics data for a specific short URL |

---

## 5. Architecture

### Load Balancer

Distribute incoming requests across multiple servers to handle large-scale traffic.

Responsibilities:

- Traffic distribution
- Health checks
- Failover
- SSL termination
- Global routing

### Hash-Based URL Mapping

Use a unique ID and Base62 encoding to generate compact short URLs.

```text
Long URL
   |
   v
Unique ID Generator
   |
   v
Numeric ID
   |
   v
Base62 Encoder
   |
   v
Short Code
   |
   v
https://tiny.url/abc123
```

### Microservices

Separate services for:

- URL shortening
- Redirection
- Analytics
- User management
- Abuse detection

### Event Queue

Use **Kafka / RabbitMQ** for handling analytics updates asynchronously.

Events include:

- Click events
- Geographic data
- Device information
- Browser information
- Timestamp
- Referrer data

## 7. URL Generation

### Base62 Encoding

Base62 uses:

```text
a-z -> 26 characters
A-Z -> 26 characters
0-9 -> 10 characters

Total = 62 characters
```

A numeric ID can therefore be converted into a compact URL-safe string.

### URL Generation Flow

```text
Long URL
   |
   v
Unique ID Generator
   |
   v
Numeric ID
   |
   v
Base62 Encoder
   |
   v
Short Code
   |
   v
tiny.url/{shortCode}
```

### Example

```text
Numeric ID
1256327512
     |
     v
Base62
abc123
     |
     v
https://tiny.url/abc123
```

### Why Base62?

- Compact
- URL-safe
- Efficient
- Easy to generate
- Avoids special URL characters
- Provides a large keyspace

## 8. Kind of Data Store

### Relational Database

Use **MySQL / PostgreSQL** for:

- URL mappings
- Long URLs
- User details
- Custom aliases
- Expiration metadata
- URL ownership

Example:

| id | short_code | long_url | user_id | expires_at |
|----|------------|----------|---------|------------|
| 101 | abc123 | https://example.com | 501 | NULL |
| 102 | xyz789 | https://openai.com | 502 | 2027-01-01 |

### NoSQL Database

Use **DynamoDB / MongoDB / Cassandra** when very large-scale distributed URL storage is required.

Useful for:

- High read throughput
- Horizontal scaling
- Distributed URL mappings
- Large URL datasets

### Analytics Store

Use:

- ClickHouse
- BigQuery
- Elasticsearch

for large-scale analytics workloads.

### Redis

Use Redis for:

- Frequently accessed URL mappings
- Hot short URLs
- Cache entries
- Rate limiting
- Temporary metadata

---

## 9. Scaling of DB

### Horizontal Scaling

Partition URL mappings based on a hash of the short URL.

```text
                     URL Traffic
                          |
                          v
                    Hash Function
                          |
             +------------+------------+
             |            |            |
             v            v            v
          Shard 1       Shard 2      Shard N
```

### Geographic Partitioning

For global deployments:

```text
Global Traffic
      |
      +---------------+----------------+
      |               |                |
      v               v                v
 North America      Europe            Asia
      |               |                |
      v               v                v
 URL Shards        URL Shards       URL Shards
```

### Replication

Use read replicas for:

- High query traffic
- Faster reads
- Failover
- Better availability
- Reduced latency

---

## 10. Caching & Sharding

### Caching

Use **Redis / Memcached** to cache frequently accessed URL mappings.

```text
Client
  |
  v
Redirect Service
  |
  v
Redis
  |
  +---- Cache Hit ------> Original URL
  |
  +---- Cache Miss
          |
          v
       Database
          |
          v
       Original URL
          |
          v
       Update Redis
```

### Cache Strategy

Use:

- LRU eviction
- TTL
- Cache warming for popular URLs
- Negative caching for invalid URLs

### Sharding

Shard URL mappings based on:

```text
hash(shortCode)
```

or:

```text
shortCode prefix
```

This distributes URL mappings across database nodes.

---

## 11. Failure & Fault Tolerance

### Replication

Maintain multiple replicas of URL data to prevent data loss during failures.

### Fallback Mechanism

Retry failed requests or serve cached responses when databases are temporarily unavailable.

```text
Redirect Request
      |
      v
Redis Cache
      |
      +---- HIT ------> Redirect
      |
      +---- MISS
            |
            v
         Database
            |
            X Failure
            |
            v
       Replica / Retry
```

### Retry

Use:

- Exponential backoff
- Maximum retry limits
- Request timeouts
- Controlled retries

### Circuit Breakers

Prevent cascading failures by isolating unhealthy services.

```text
Redirect Service
      |
      v
Database
      |
      X
   Failure
      |
      v
Circuit OPEN
      |
      v
Fallback / Cache
```

### Additional Fault-Tolerance Techniques

- Health checks
- Automatic failover
- Multi-region replication
- Dead-letter queues
- Idempotent APIs
- Graceful degradation
- Rate limiting

---

## 12. Logging & Security

### Logging

Use centralized logging such as the **ELK Stack**.

```text
Services
   |
   v
Log Collector
   |
   v
Elasticsearch
   |
   v
Kibana
```

Monitor:

- Redirect latency
- URL creation rate
- Cache hit ratio
- Database errors
- Invalid URLs
- Traffic spikes
- API errors
- Service health

### Security

1. Use HTTPS for all APIs and redirections.
2. Validate submitted URLs.
3. Block malicious and phishing URLs.
4. Implement rate limiting.
5. Protect analytics endpoints with authentication.
6. Apply authorization for private analytics.
7. Prevent URL enumeration where appropriate.
8. Scan URLs against threat-intelligence systems.
9. Protect APIs against DDoS attacks.
10. Log suspicious activity.
11. Sanitize user-controlled input.
12. Apply abuse detection and throttling.

# Key Design Principles

- **Hash / ID-based URL generation**
- **Base62 encoding for compact short codes**
- **Redis caching for ultra-fast redirects**
- **301 redirects for permanent mappings where appropriate**
- **Kafka for asynchronous analytics**
- **MySQL/PostgreSQL for durable URL mappings**
- **NoSQL for massive distributed workloads**
- **ClickHouse/BigQuery for analytics**
- **Horizontal database scaling**
- **Hash-based sharding**
- **Read replicas**
- **Multi-region deployment**
- **High availability**
- **Rate limiting and abuse prevention**
- **HTTPS everywhere**
- **URL validation and phishing protection**
- **Circuit breakers and retries**
- **Centralized logging and monitoring**

# Most Important Design Decision

The **redirect path is the critical hot path**.

Therefore:

```text
                         REDIRECT HOT PATH

User
 |
 v
Load Balancer
 |
 v
Redirect Service
 |
 v
Redis
 |
 +---- Cache HIT -----> 301 Redirect
 |
 +---- Cache MISS
          |
          v
       Database
          |
          v
        Redis
          |
          v
      301 Redirect
```

Analytics must remain **asynchronous** so click tracking never becomes a bottleneck for the actual redirect.
